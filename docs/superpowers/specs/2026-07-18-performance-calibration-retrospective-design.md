# LumaSR 真机性能校准复盘设计

## 现状与根因

REDMI K90 Pro Max 的 Vulkan、FP16 与质量门已经通过真实推理验证，但现有生产校准仍存在以下结构性问题：

- Android 接线只测量 `tile=128`、`batch=1` 和 CPU 基线，不会搜索已实现的候选空间。
- Vulkan FP16 在该固定候选上比 FP32 慢约 12%；这是性能门未通过，不是质量失败。
- 任一分辨率档未达到 5% 提速就终止整轮校准，因此 CPU 结果和“继续使用兼容模式”的负证据都不会保存。
- `RuntimePipelineDepthPolicy` 的生产审批固定为 `false`，原生 depth 2 双缓冲没有生产启用路径。
- 校准曾让 FP32、FP16、CPU 三种模型身份互相驱逐，导致正式样本都包含模型加载；容量 3 的修复已有单测，但尚无最新真机证据。
- 早期完整候选搜索曾产生 GiB 级 PSS/Native Heap，扩大搜索前必须同时增加候选预检与运行时资源看门狗。

进度百分比、终端自动滚动、终态日志重复、Android 8–9 SAF 保存、持久任务回收、动态温控以及固定 APK 签名已经修复，本轮仅增加回归保护，不重新设计这些稳定路径。

## 结果语义与持久化

校准记录升级为 schema v5。每个 Vulkan 分辨率档持久化一个终态：

- `ENABLED`：质量通过，最终候选至少比 FP32 快 5%，并携带可启用 profile。
- `QUALITY_REJECTED`：质量证据有效但不满足固定质量门，继续使用兼容模式。
- `PERFORMANCE_REJECTED`：质量通过，但完整 tile、batch、depth 搜索后仍未达到速度门。

质量或性能未达标属于有效的安全校准结论，不再映射为运行故障。探针失败、输出无效、资源越界、Moderate 及以上温控、总超时和持久化失败仍不发布记录。

旧 schema v3/v4 继续可读取，但新的 benchmark 身份键会使其失效；旧记录不得解锁 v5 搜索或 depth 2。负证据与正向 profile 使用相同的 30 天有效期和模型、构建、设备、驱动身份约束。

## 有界自适应搜索

- 总预算保持 5 分钟并为发布和清理预留 15 秒。
- Vulkan tile 最大集合为 `64/128/256`，batch 为 `1/2/4`。先选最快 FP16 tile，再搜索 batch，最后统一比较 FP32，避免 batch 尚未测量就提前拒绝。
- CPU 使用坐标下降搜索 tile、设备拓扑线程、`blocktime=0/20ms`、`postprocess=1/2`；重复候选去除，线程上限为 8。
- 新模型缓存身份先用 512 输出预热。正式性能样本必须报告 `cacheHit=1`；否则只允许重新预热和复测一次。
- 初筛每候选一次。拟启用候选与基准各复测一次，两次配对比较均满足门槛才启用；平局选择更保守的 tile、batch、depth 和线程配置。
- 单次探针最多 45 秒。可选 CPU/TTA 候选超时后停止对应搜索并使用安全默认；质量门、Vulkan 基准或输出验证超时则整轮失败。

## 资源、温控与 depth 2

- 单 slot 估算不超过 64MiB；双 slot 不超过 128MiB。
- depth 2 还必须满足 GPU heap 25%、可用 RAM 15%、非 Low-RAM、Vulkan OPTIMIZED、Normal/Light 和非 TTA 条件。
- 校准期间每秒采样 PSS、Native Heap、低内存与温控；相对会话基线增量超过 128MiB或系统进入低内存时取消当前 JNI 工作。
- depth 2 只在同一 tile/batch 下比 depth 1 快至少 10%，且最终仍比 FP32 快至少 5% 时写入 profile。
- 运行时只能降低校准 profile 给出的最大深度，不能自行升级；旧任务和旧记录默认 depth 1。

## UI、日志与兼容性

UI 区分“校准完成并启用优化”“校准完成但保持兼容模式”“校准失败”。日志保留候选参数、耗时、速度差、缓存命中、模型加载、pipeline depth 和跳过原因，不记录图片路径。

校准开始时建立最大步骤计划；未执行候选以 `STEP_SKIPPED` 结算工作量，确保步骤数、进度和 ETA 不倒退。完整日志和最终结果继续保留到用户主动关闭。

不新增依赖、权限、模型或 `largeHeap`，不改变质量门、`minSdk`、固定签名和稳定回退路径。
